## SPEC — 성향 용어 사전 (ego_terms)

> 선문후코. 이 문서 확정 후 코드 착수. 관련: `docs/simhwa/SPEC.md` §14(심화 컬러 코딩), `요청.26.0729.1520-M2A7월28일수정요청`.

### 1. 왜 짓는가

피터공 2026-07-29: *"이 부분에서 문제가 안 생기도록 룩업테이블이든 뭐든 용어 정리 시스템을 구축하자. 이것이 사용중 바뀌면 매우 큰 문제야."*

손소장 7/28 수정요청 1번(`CP(원칙,결단)`·`AC(순응,협조)`로 변경)을 검토하다 드러난 것 — **성향의 이름과 색이 코드 곳곳에 복사돼 있어, 이름 한 번 바꾸려면 여러 파일을 동시에 맞춰야 한다.** 한 곳만 놓치면 같은 사람이 리포트 안에서 두 이름으로 불린다.

실측(2026-07-29):

| 무엇 | 정의가 복사된 곳 | import |
|---|---|---|
| 라벨(기준·결단 등) | `scoreEngine.js` · `ReportPageV2.jsx` · `InsightCharts.jsx` · `SimhwaReportView.jsx`(EGO_PLAIN + LABEL_TO_CODE) — **5곳** | 0 |
| 색(#ef4444 등) | `ResultPage` · `InsightCharts` · `AdminDashboard` · `ReportPageV2` · `CampaignAnalytics` · `SimhwaReportView` — **6곳** | 0 |
| 강점명(또렷한 기준 등) | `ReportPageV2.jsx` 1곳 | - |
| 유형명(기준을 세우는 힘 등) | `ReportPageV2.jsx` 1곳 | - |
| 매칭 정규식 | `ReportPageV2.EGO_LABEL_RE` · `SimhwaReportView.COLOR_RE` — 2곳, 규칙이 미묘하게 다름 | - |

값은 지금 전부 일치한다. 문제는 **일치를 강제하는 장치가 없다**는 것.

### 2. 지금 구조에서 이미 잘 되고 있는 것 (건드리지 않는다)

조사 전에 세운 가설("산문 400곳에 이름이 박제돼 있다")은 **틀렸다.** 렌더러가 이미 절반쯤 룩업으로 동작한다.

- `colorizeEgo`(성향리포트)의 `EGO_LABEL_RE = /(CP|NP|FC|AC|A)\([가-힣,·]+\)/g` 는 산문 속 `CP(기준,결단)`을 잡아 **괄호 안 글자를 버리고 상수 값으로 다시 쓴다.** → `cm_manager.yaml` 198곳·`cm_coach.yaml` 220곳은 yaml을 안 고쳐도 이름이 바뀐다.
- `colorize`(심화)는 여기에 **맨 라벨**(`기준·결단`) 매칭을 더했다. → `simhwa_gen.yaml` 61곳도 자동.
- 둘 다 라벨 뒤에 ' 성향'이 없으면 붙이고 조사를 교정한다. 그래서 조사는 대개 라벨이 아니라 '성향'(받침 ㅇ) 뒤에 온다.

**따라서 이 SPEC은 산문을 고치지 않는다.** 산문은 이미 옳은 방식으로 쓰여 있다. 고치는 것은 상수가 흩어진 것과, 매칭 규칙이 두 벌인 것.

### 3. 진짜 박제 (사전으로도 안 풀리는 곳)

`simhwa_static.yaml`의 `customer_title` 5줄. `SimhwaReportView`의 `<h3>{c.title}</h3>`가 colorize를 안 지나 텍스트 그대로 나간다.

```
customer_title.CP: 기준·결단 성향 고객을 10분 만에 알아보는 방법
```

→ **사전에서 조립하도록 바꾼다**(§6-3). 마침 손소장 7/28 항목 6이 이 다섯 줄 교체를 요청 중이라 함께 처리한다.

### 4. 조사 함정 (이번에 드러난 것, 사전이 막아야 할 것)

현행 다섯 라벨은 **전부 받침으로 끝난다**(결단·공감·판단·표현·조율). 코드가 이 우연에 기대고 있고, `ReportPageV2.jsx:147` 주석이 그걸 명시한다: *"EGO_STRENGTH 다섯 값 모두 받침으로 끝나 조사는 항상 '과' → 플레이스홀더 '과(와)' 고정"*.

손소장이 요청한 `순응·협조`는 **받침이 없다.** 그대로 넣으면 인물상 fallback 문장이 "세심한 조율과" → "…협조과"로 깨진다. 라벨을 안 바꾸기로 했으므로 지금 당장 깨지지는 않지만, **다음 이름 변경 때 반드시 밟는 지뢰**다. 사전이 조사를 계산해 제공한다(§5-3).

### 5. 사전 설계

#### 5-1. 데이터 — `src/data/ego_terms.yaml`

성향 하나당 한 블록. **화면에 나가는 이름·색은 전부 여기서만 나온다.**

```yaml
order: [CP, NP, A, FC, AC]        # 그래프 축·표지 칩·리스트 순서 (점수순 아님)
tie_priority: [A, CP, NP, FC, AC] # 동점 우선순위 (손소장 26.0611)

terms:
  CP:
    label: 기준·결단              # 정본 표기. 그래프 축·본문·CSV·표지 칩
    color: '#ef4444'              # 기본 색
    tint:  '#fef2f2'              # 옅은 배경 (admin 카드)
    ink:   '#dc2626'              # 진한 글자색 (admin 카드)
    strength: 또렷한 기준          # 인물상 fallback 문장용
    type_name: 기준을 세우는 힘     # top1 강조용
    aliases: []                   # 산문에 남아 있는 옛/변형 표기
```

**`aliases`가 이 사전의 핵심.** 매칭은 별칭까지 훑고, 출력은 언제나 `label`로 한다. 이름을 바꿀 때 옛 표기를 `aliases`에 내려놓기만 하면, 산문 400여 곳을 안 건드리고도 화면이 새 이름으로 바뀐다. 지금은 전부 비어 있다(정본과 산문이 일치하므로).

> ⚠️ `aliases`에 넣는 것은 **맨 라벨 형태만**이다. `CP(기준,결단)` 같은 괄호형은 정규식이 코드로 잡으므로 별칭이 필요 없다.

#### 5-2. 로더 — `src/lib/egoTerms.js`

yaml을 읽어 파생값까지 만들어 내보낸다. **파생은 여기서만, 소비처는 읽기만.**

```js
export const EGO_ORDER        // ['CP','NP','A','FC','AC']
export const TIE_PRIORITY
export const EGO_LABEL        // {CP:'기준·결단', …}
export const EGO_COLOR        // {CP:'#ef4444', …}
export const EGO_TINT, EGO_INK
export const EGO_STRENGTH, EGO_TYPE_NAME
export const LABEL_TO_CODE    // 정본 + aliases 전부 → 코드
export function egoTermRe()   // CODE(…) | 정본라벨 | 별칭  (매칭 규칙 단일 출처)
export function labelOf(code)
```

`egoTermRe()`는 두 렌더러가 각자 갖고 있던 정규식을 하나로 합친 것. 별칭이 늘면 정규식도 자동으로 따라온다. **상수가 아니라 함수인 이유** — `/g` 정규식은 `lastIndex`를 들고 다녀서, 공유 인스턴스를 두 컴포넌트가 동시에 쓰면 매칭이 어긋난다. 호출할 때마다 새로 만든다. 별칭이 긴 것부터 매칭하도록 정렬해 부분 일치로 잘리는 것도 막는다.

#### 5-3. 조사 — `src/lib/josa.js` (egoTerms가 재수출)

**사전과 분리한 파일에 둔다.** yaml을 import하는 모듈은 vite 밖(노드)에서 못 불러와 검사가 안 된다. 조사 규칙은 데이터 의존이 없는 순수 함수라, 떼어 두면 `check-ego-terms.mjs`가 노드에서 직접 돌려 볼 수 있다.

```js
export function hasBatchim(word)          // 마지막 글자 받침 유무
export function josa(word, pair)          // josa('순응·협조','이/가') → '가'
export function withJosa(word, pair)      // → '순응·협조가'
export function joinWithJosa(words)       // ['또렷한 기준','따뜻한 공감'] → '또렷한 기준과 따뜻한 공감'
```

지원 쌍: `이/가` · `은/는` · `을/를` · `과/와` · `으로/로`(ㄹ 받침은 '로') · `이라/라`.
라벨이 바뀌어도 조사가 따라온다. `ReportPageV2`의 하드코딩 '과'를 이걸로 교체한다.

### 6. 소비처 개편 (값은 한 글자도 안 바뀐다)

리팩터링이지 기능 변경이 아니다. **화면 산출물은 개편 전후가 픽셀 단위로 같아야 한다**(§8 회귀 기준).

1. **상수 제거 → import**: 라벨 5곳·색 6곳·강점명·유형명. `_archive/`는 손대지 않는다(죽은 코드).
2. **정규식 통합**: `EGO_LABEL_RE`·`COLOR_RE` → `EGO_TERM_RE`. 두 `colorize` 함수의 미묘한 차이는 유지(성향리포트는 코드형만, 심화는 맨 라벨까지)가 아니라 **심화 쪽 규칙으로 통일** — 성향리포트 산문에는 맨 라벨이 없어(측정 완료: 박제 0곳) 통일해도 출력이 바뀌지 않는다.
3. **`customer_title` 조립화**: `simhwa_static.yaml`의 다섯 줄을 지우고, 사전의 `templates.customer_title`(`'{label} 성향 고객을 10분 만에 알아보는 방법'`)에 `customerTitle(code)`가 이름을 주입한다. 조립은 `buildSimhwa`에서.
4. **`scoreEngine.TIE_PRIORITY`**도 사전으로 옮긴다(같은 성격의 흩어진 상수).

### 7. 드리프트 검사 — `scripts/check-ego-terms.mjs`

사전을 지어도 **다음 사람이 또 복사하면** 원위치다. 그래서 검사를 붙인다.

네 가지를 본다.

1. **사전 값 = 개편 전 정본.** 스크립트 안에 2026-07-29 시점 리터럴을 `FROZEN`으로 얼려 두고 8개 항목 × 5성향을 대조한다. 값 추출 리팩터링이 값을 흘리지 않았는지 보는 것 — 성향리포트(`/report/:id`)는 supabase가 필요해 렌더 덤프를 못 뜨므로, 그 화면은 이 검사가 지킨다. **라벨을 의도적으로 바꿀 때는 `FROZEN`도 함께 고친다**(그때는 화면이 바뀌는 게 맞으므로).
2. **재정의 탐지.** `{ CP: '…'` 꼴 객체 리터럴에 색(#hex)이나 한글이 박혀 있으면 복사본으로 보고 실패시킨다. 예외는 사전 로더(`lib/egoTerms.js`) 하나. 점수 범위 같은 숫자 맵은 통과시킨다.
3. **산문 속 미등록 표기.** `src/data/*.yaml`에서 `가나·다라`/`가나,다라` 꼴을 훑어, 사전의 정본도 별칭도 아닌 것을 잡는다(표기 흔들림·오타·별칭 등록 누락). 괄호형 `CP(무엇이든)`은 렌더러가 코드로 잡으므로 대상이 아니고, 주석 줄도 화면에 안 나가므로 뺀다.
   **잡는 조건 두 가지** — (가) **두 낱말 모두** 사전 어간(뒤섞인 표기: `친화·공감`) / (나) **한 낱말이 사전 어간이면서 바로 뒤에 '성향'이 붙음**(새 이름을 산문에 박은 경우: `원칙·결단 성향`).
   조건을 이렇게 좁힌 것은 실측 결과다. 처음엔 "한 낱말만 겹쳐도" 잡게 했더니 `눈치, 조율`·`발함, 표현`·`보다, 기준` 같은 평범한 쉼표 산문이 19건 걸렸고, '성향'만 봐도 `…한다면, 해당 성향은`이 걸렸다. **오탐이 나면 아무도 검사를 안 보게 된다.** 최종 규칙으로 오탐 0, 오염 주입 테스트(새 이름 박제·뒤섞인 오타)는 둘 다 탐지.
4. **조사 규칙.** 받침 있는 이름(협조·조율 — ㄹ 받침)·받침 없는 이름(순응·협조)·일반 받침(기준·결단) 아홉 경우. 사전 라벨 중 받침 없는 것이 있으면 어떻게 나가는지 참고로 찍는다.
5. **금지 어휘.** `src/data/*.yaml`에 실리면 안 되는 낱말이 들어왔는지 본다. 현재 `MBTI` 하나 — 과학적 근거 없는 유형론을 겹쳐 설명하면 놀공 산출물의 신뢰가 깎인다는 피터공 판단(2026-07-29). 손소장 원문 시트1의 **각 편 2번째 줄**에 5줄 들어 있어, 통째로 복사하면 딸려 들어가는 자리다. 사람 주의력이 아니라 검사로 막는다. 목록은 `BANNED` 배열 — 같은 성격의 낱말이 생기면 여기 추가.

`npm run check:terms`로 실행. **빌드를 막지는 않는다** — 배포를 세우는 부작용이 더 크다.

### 9. 라벨 변경 — 손소장 확정 (2026-07-29, 사전 도입 당일 오후)

사전을 지은 뒤 손소장 회신이 와서 **다섯 라벨을 전부 새 표기로 바꿨다.** 사전이 실제로 값을 하는 첫 사례.

| 코드 | 옛 표기 → `aliases` | 새 정본 `label` | 받침 |
|---|---|---|---|
| CP | 기준·결단 | **원칙·결단** | 있음 |
| NP | 배려·공감 | **공감·배려** | **없음** |
| A | 이성·판단 | 이성·판단 (변동 없음) | 있음 |
| FC | 친화·표현 | 친화·표현 (변동 없음) | 있음 |
| AC | 협조·조율 | **순응·협조** | **없음** |

손소장 확정 문구: *"NP는 공감 배려는 그대로 하고요 / A는 이성 판단으로 하고요 / 나머지는 CP 원칙 결단, FC 친화 표현, AC 순응 협조 맞습니다 / 성향코칭 리포트와 심화코칭 리포트 모두 수정 부탁해요"*. A는 링크 시트2의 `이성·분석`이 아니라 **`이성·판단`**으로 확정(시트 안 불일치 해소).

**범위 — 손소장이 말한 두 리포트보다 넓다.** 다섯 낱말이 시스템 전체의 한 벌이라 관리자·코치 리포트, 결과화면, admin 대시보드·CSV까지 함께 바뀐다. 어휘를 리포트별로 갈라 두면 같은 사람이 화면마다 다른 이름으로 불리므로, **한 벌 유지가 맞다**고 판단해 전면 적용.

**받침 없는 라벨이 둘 생겼다**(공감·배려·순응·협조). §4에서 지적한 지뢰가 실제로 밟힌 것 — `josa.js`가 조사를 계산해 막는다.
