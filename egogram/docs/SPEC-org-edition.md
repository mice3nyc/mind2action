## 0. 현재 상태 (코드 실측, 10/20)

- **리포트 종류는 응답자가 고른 역할(jobType)이 정한다.** 캠페인에는 리포트 종류 설정이 없다(`CampaignManager.jsx` EMPTY_FORM = 고객사·대상·예상 인원·기간·교육일).
  - 역할 → 문안: `cmLookup.js` JOB_TO_CM (sales→cm_insurance, coach→cm_coach, sales_leader→cm_manager)
  - 역할 → 안전구간: `scoreEngine.js` JOB_TO_ROLE
  - 역할 → 리포트 종류 이름·심화 대상: `reportType.js` JOB_TO_REPORT
  - 역할 라벨: `SurveyIntro.jsx` JOB_OPTIONS · `resultLabels.js` JOB_LABELS · `CampaignAnalytics.jsx` JOB_LABELS/ROLE_OF — **세 군데에 따로 적혀 있다**
- **관리자 = 공유 계정 1개**(`admin@mind2action.kr`, 피터공·손소장). RLS가 「로그인했으면 전부 조회·삭제」라 계정을 늘려도 볼 수 있는 범위는 못 가른다.
- **배포** = gh-pages 브랜치 루트 + CNAME `survey.mind2action.kr`, `npm run deploy`(`--add`). Supabase 주소·키는 `VITE_SUPABASE_URL`·`VITE_SUPABASE_ANON_KEY`로 이미 빌드 시 바꿀 수 있다(`lib/supabase.js`).
- **스키마 파일이 라이브와 다르다** — `supabase-schema.sql`은 RLS가 옛 「전면 개방」이고 `campaigns` 테이블이 없다(정의는 `CAMPAIGNS.md` §, 보안 정책은 `ADMIN-SECURITY.md`). 새 프로젝트를 이 파일로 만들면 틀린 DB가 생긴다.
- 기존 관리자 문안(`cm_manager.yaml`)은 「고객에게 안부전화」 「보장분석과 설계활동」 등 보험 문장이 본문에 박혀 있어 일반 조직에 못 쓴다.

## 1. 분리 모델

| 축 | 보험판 (현행) | 일반 조직판 (신설) |
|---|---|---|
| 코드 | 같은 저장소·같은 `src/` | 같음. 빌드 시 `VITE_EDITION=org` |
| 주소 | `survey.mind2action.kr/` | `survey.mind2action.kr/org/` |
| Supabase | Mind2Action 프로젝트 | **새 프로젝트** (데이터·계정 완전 분리) |
| 관리자 계정 | `admin@mind2action.kr` 공유 | `master@mind2action.kr`(피터공·애련공) · `son@mind2action.kr`(손소장) |
| 역할 선택지 | 고객 컨설팅 영업 / 신인 육성 코칭 / **리더(보험 조직 운영)** | **리더(일반 조직 운영)** |
| 리포트 문안 | cm_insurance · cm_coach · cm_manager | **cm_org_leader.yaml (신설, 손소장 링크 포맷)** |
| 관리 화면 | 현행 그대로 | 청색 테마 (레이아웃 동일) |

- 저장소를 복제하지 않는 이유: 점수 엔진·리포트 틀·관리 화면을 같이 쓰므로, 고친 것이 양쪽에 한 번에 간다. 복제하면 이후 수정이 두 벌이고 운영은 놀공이 계속한다(10/19).
- 한 앱 안에서 캠페인으로 가르지 않는 이유: 정산이 걸린 라이브 DB의 RLS를 고쳐야 하고, 실수 하나로 보험사 응답자 개인정보가 다른 기관 사람에게 보인다.
- 별도 서브도메인 대신 `/org/` 경로인 이유: Pages 사이트 하나에는 커스텀 도메인 하나뿐이라 서브도메인은 저장소를 하나 더 만들어야 한다. 경로는 DNS 작업이 없다. 나중에 서브도메인이 필요하면 그때 옮긴다.

## 2. 에디션 스위치

- `src/lib/edition.js` 한 파일이 에디션별 값을 쥔다: 역할 선택지·라벨·역할→문안·역할→리포트 종류·역할→안전구간 키·관리 화면 테마 클래스·탭 제목.
- §0의 여섯 군데는 이 파일을 읽도록 바꾼다. **보험판은 값이 지금과 글자까지 같아야 한다**(라벨 하나 바꾸는 것 말고는 회귀 0).
- `.env.org` = `VITE_EDITION=org` + 새 Supabase URL·anon 키. 빌드 `vite build --mode org --base /org/`.
- 일반판에서 보험 전용 기능은 닫는다: **심화코칭**(`isSimhwaTarget`이 보험설계사만 → 일반판에서는 버튼 자체가 안 뜬다, 확인만).

## 3. 일반판 리포트 문안

- `src/data/cm_org_leader.yaml` 신설. 구조는 `cm_manager.yaml`과 같은 키(cm1·cm2·cm4_1·cm4_2·cm4_4·…)를 쓰고 본문만 손소장 포맷으로 채운다 — 리포트 렌더 코드는 그대로 둔다.
- **재료 = 손소장이 보낸 「리더(일반 조직 운영)」 포맷 링크. 아직 받지 못함.** 받은 뒤 포맷이 기존 키 구조에 안 맞으면 이 절을 먼저 고친다.
- 안전구간: 현재 세 역할 모두 UNIFIED_RANGES. 일반판 리더도 같은 값으로 시작(손소장이 다르게 주면 그때).

## 4. 계정과 권한

- 새 Supabase 프로젝트의 Auth에 두 계정. 둘 다 실제 메일함 아님(기존 admin@와 같음), 비번은 사람끼리 공유하고 코드에 안 둔다.
- 권한 구분은 Auth 사용자의 `app_metadata.role` = `master` | `son`, RLS가 이 값을 읽는다.
- **기본안(승인 대기)**: son = 조회·캠페인 생성/수정·리포트·CSV 전부, **삭제(응답·캠페인)만 master**. 관리 화면은 son 로그인 시 삭제 버튼을 숨긴다(RLS가 진짜 막고, 화면은 가림).
- 주의: 손소장은 Supabase **조직 Owner**다(10/11 추가, 10/19 유지 결정). 새 프로젝트를 같은 조직에 만들면 손소장은 대시보드에서 DB를 직접 볼 수 있다 — 앱 권한과 별개. 의도와 맞는지 확인.

## 5. 청색 테마 (관리 화면만)

- **레이아웃·간격·글자 크기·컴포넌트 변경 0.** CSS 변수와 바탕만 바꾼다. 루트에 `.edition-org` 클래스를 달고 그 아래에서만 덮는다.
- 보험판도 이미 버튼·강조가 파랑(#0012de)이라 **강조색만 파랗게 하면 구별이 안 된다.** 그래서 면 전체를 바꾼다: 연청 바탕 + 얇은 모눈(blueprint) + 상단 진청 띠에 「일반 조직판」 표기. 라운딩은 기존 그대로(레이아웃 불변 원칙이 우선).
- 참여자가 보는 설문·결과·리포트 화면은 바꾸지 않는다 — 혼동은 운영자 쪽 문제다.
- 탭 제목도 「MIND2ACTION 관리 · 일반 조직」으로 갈라 브라우저 탭에서 구별되게.

## 6-1. 일반판에서 보험업 흔적 걷어내기 (10/20 전수 조사)

> 손소장은 「소득란에 스킵해도 된다고 노티스」를 제안했으나 피터공 10/20 결정: **소득 구간은 설계사용이니 일반판에서 뺀다.** 그 밖의 보험 냄새는 아래 전수 결과로 판단한다.
> 조사 방법: 보험 어휘(보험·설계·고객·계약·영업·상담·보장·컨설턴트·소득·리크루팅·신인·지점·매출·안부전화·활동량 등) grep → 일반판 리더 리포트에 **실제로 렌더되는 경로**만 남김. `현실적`이 `실적`에 걸린 오탐 제외.

**뺀다(결정)**
- 설문 첫 화면 「직전 3개월 평균 소득」 칸 → 일반판에서 제거. 따라 나가는 것: 관리 표 「소득」 열·정렬, CSV 「소득」 열, 캠페인 분석의 「소득 상위 대 하위」 비교. (CSV 「리크루팅」 열은 이미 안 쓰는 옛 칸 — 같이 뺀다)

**고칠 후보(피터공·손소장 판단)**
1. 리포트 **§4 「성과에 도움이 되는 말투」(cm5)** — 리더 리포트의 보험 냄새가 거의 여기 몰려 있다. 120문단 중 58문단에 「고객에게 안부전화」 「보장분석과 설계활동」 「계약」 「매출」 「활동량」. → 손소장 일반판 포맷으로 새로 써야 하는 핵심 구간
2. 리포트 머리 「성향 코칭 리포트의 목적」 셋째 항목 — 「비지니스를 하는 사람은 … 상담을 원하는 방향으로 이끌 수 있고」. 영업 상담 맥락
3. 설문 39번 문항 「상담이나 회의 중 분위기가 가라앉으면」 — 「대화나 회의 중」 정도면 일반. **문항을 바꾸면 보험판과 같은 50문항이 아니게 된다**(점수 비교 기준이 갈린다) → 손소장 판단
4. 첫 화면 「소속」 칸 예시 `OO지점` → 일반 표현(`OO부서`)
5. 첫 화면 「경력(개월)」 — 보험 냄새는 아니나 교사·공무원은 연 단위가 자연스럽다. 유지 기본

**문제없음(확인)**
- 50문항 중 39번 외 49개는 일반 문항(42번 「아이들을 돌보는」은 보험과 무관)
- 리포트 §1 성향·§2 말투(cm2의 「상담」 3건은 「구성원과의 상담」 — 조직 내부 면담이라 일반 조직에도 맞음)·§3 강점·조율 포인트(cm4)·인물상·명언·맺음말
- 「클로징 전 고객님이 거절시」(cm6)·「신인 리크루팅」(cm7)·보험 상담 제목(ego_terms customer_*)·심화코칭 → 전부 보험설계사 역할에서만 렌더. 일반판엔 안 나온다

## 7. 배포 위험과 대책

- **`npm run deploy:clean`(보험판)은 브랜치 전체를 갈아 `/org/`를 지운다.** → 스크립트를 일반판 폴더를 보존하는 형태로 고치거나 폐기. 고치기 전에는 쓰지 않는다.
- 일반판 배포 = `gh-pages -d dist-org --dest org --add`. `public/CNAME`이 `/org/`에 따라 들어가지 않게 뺀다.
- 새 Supabase 스키마는 **라이브 DB에서 DDL을 뽑아** 만든다(스키마 파일 불신, §0). 뽑은 DDL을 `supabase-schema.sql`에 정본으로 갱신해 다음 사람이 같은 함정에 안 빠지게 한다.
